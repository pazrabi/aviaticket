# Задачи для droidhub (для разработчика хаба)

Репозиторий: https://github.com/pazrabi/droidhub.git, ветка `main`. Правила и контракты хаба: `CLAUDE.md`, `PLAN.md`, `JOURNAL.md` в том репозитории (читать первыми, журнал вести).

Зачем это нужно. Бот цен авиабилетов (avia-bot) сейчас вызывает `fetch_page`, который отдаёт ВСЁ одним ответом в самом конце ожидания и без времени. Из-за этого бот вынужден ждать полный срок каждого сайта (до 45–60 с), даже если лучшая цена пришла на 8-й секунде. Нужно, чтобы бот видел JSON-ответы сайта по мере прихода и сам решал, когда остановиться, и чтобы проигравший или ненужный запрос можно было отменить и сразу освободить телефон.

Хаб цены не разбирает и разбирать не должен: все парсеры остаются в боте. Хаб только отдаёт сырые ответы, время и состояние.

Две части. Часть A маленькая и выкладывается первой: с ней бот уже начинает копить данные. Часть B большая.

---

## Часть A. Время в старом `fetch_page` (выложить первой)

Файлы: `hub/devices/browser.py`, `hub/api/routes.py`, `tests/test_browser.py`, `tests/test_routes.py`, `docs/agent-guide.md`.

1. К каждому элементу `json_responses` в ответе `fetch_page` добавить поле `t` — секунды (float, 2 знака) от момента `Page.navigate` до `Network.loadingFinished` этого запроса.
2. В корень ответа добавить:
   - `woke` (bool): будили ли экран перед этим запросом;
   - `t_first_match` (float | null): секунды до первого ответа, подошедшего под `capture_json` (первый «нужный» JSON).
3. Поля только ДОБАВЛЯЮТСЯ. Всё, что есть сейчас, остаётся как есть. MCP-инструменты не меняются. Существующие тесты проходят без правок.

Готово, когда: тест с поддельным CDP показывает, что `t` растёт по порядку прихода ответов; `woke` истина, если экран был выключен; `t_first_match` null, если подходящих ответов нет.

Почему первым: бот пересчитывает по этим `t` хронологию цен (как менялся минимум по ходу загрузки) и по ней выбирает для каждого сайта, через сколько секунд тишины можно останавливаться.

## Часть B. Задания на загрузку (job)

Файлы те же. Старый `fetch_page` и MCP остаются.

### Маршруты
- `POST /api/devices/{id}/fetch_jobs` — те же поля, что у `fetch_page` (`url`, `wait_seconds`, `capture_json`, `max_chars`, `wait_for`, `wait_full`; список полей брать из актуальной сигнатуры `fetch_page` в `hub/devices/browser.py`), плюс `max_seconds` (не больше 90). Открывает вкладку, запускает загрузку, СРАЗУ возвращает `{"job_id": "..."}`. Если телефон занят — тот же ответ/ошибка, что и у `fetch_page` сейчас (занят/очередь).
- `GET /api/fetch_jobs/{job_id}?since=N` — новые ответы начиная с номера N:
  ```json
  {
    "responses": [{"i": 0, "t": 4.31, "url": "...", "body": "..."}],
    "next": 1,
    "state": "running | done | failed",
    "wait_for_seen": false,
    "network_quiet": false,
    "elapsed": 4.9,
    "captcha": false
  }
  ```
  - `i` — сквозной номер ответа в задании, `next` — с какого номера спрашивать дальше.
  - `t` — как в части A.
  - Каждое тело отдаётся один раз (при повторном запросе с тем же `since` тело можно не повторять, главное не терять и не дублировать при последовательном опросе с `since=next`).
  - `wait_for_seen` — встретилась строка `wait_for` (признак «выдача готова» у сайта).
  - `network_quiet` — сеть по нужным адресам (`capture_json`) молчит 1,5 с и дольше.
  - `captcha` — на странице капча.
  - Длинный опрос: если нового нет, держать запрос до 1 с и отвечать пустым списком.
- `POST /api/fetch_jobs/{job_id}/finish` — читает текст страницы, закрывает вкладку, отпускает телефон. Ответ как у `fetch_page` (`url`, `text`, `captcha`, `finished`, `seconds`), но БЕЗ повтора уже выданных тел JSON.
- `DELETE /api/fetch_jobs/{job_id}` — отмена: закрыть вкладку, отпустить телефон. Нужна для проигравшего дубля и вытеснения фона. Должна быть идемпотентной (повторный вызов не ошибка).

Авторизация и токены — как у остальных `/api/...` маршрутов.

### Правила жизни задания
1. Одно задание на телефон. Замок телефона держится от старта до `finish` или отмены.
2. По `max_seconds` задание само переходит в состояние `done` и ждёт `finish`.
3. Если клиент молчит 15 секунд (бот упал, оборвалась сеть) — АВТООТМЕНА: закрыть вкладку, снять замок. Телефон не должен зависать навсегда. Любой запрос клиента к заданию (опрос, finish) сбрасывает этот таймер.
4. Задание должно быть видно в статусе занятости телефона (`hub/devices/activity.py`) так же, как сейчас `fetch_page`.
5. Задание `failed`: если телефон отвалился или страница не открылась; причина в поле `error`. Замок при этом снимается.

### Старый `fetch_page`
Остаётся. Можно сделать его обёрткой над заданием (старт → ждать `done` → `finish`), но тогда ВСЕ его нынешние тесты должны проходить без изменений.

### Тесты
- с поддельным CDP ответы приходят по мере появления с возрастающим `t`, `since/next` не теряют и не дублируют;
- `network_quiet` и `wait_for_seen` поднимаются в нужный момент;
- `finish` закрывает вкладку и снимает замок, повторно тела не отдаёт;
- `DELETE` и автоотмена (15 с без запросов) закрывают вкладку и снимают замок; второй `DELETE` не падает;
- по `max_seconds` задание переходит в `done`;
- параллельное второе задание на тот же телефон получает отказ «занят».

Готово, когда на живом телефоне Aviasales (`/search/v3.2/results`) отдаёт куски по одному с растущим `t`, а `DELETE` посреди загрузки сразу освобождает телефон (следующее задание на него стартует без ожидания).

## Часть C (необязательная, после B): повтор POST-запроса сайта (`replay_post`)

Это НЕ существующий параметр хаба. Он живёт только в боте, в старом сборщике на Playwright (`src/avia/collector.py`, поле `SiteConfig.replay_post` в `config/sites.yaml`). Идея: страница сама делает POST к API сайта (у tutu это адрес, содержащий `/avia/offers/v2`) и по умолчанию получает только первую порцию (10 билетов). Сборщик перехватывает этот POST, повторяет его из контекста страницы с изменёнными полями тела JSON (у tutu: `sorting: cheapest`, `limit: 100`, `offset: 0`, `isNewSearch: false`) и добавляет ответ к собранным.

Через телефоны (`fetch_page` хаба) повтора нет, поэтому tutu на телефонах отдаёт только 10 билетов. Для быстрого поиска это терпимо, а для «Глубокого поиска» нужна вторая страница (`offset: 100`) и сортировка по цене.

Если делать в хабе (после части B, по решению ведущего): в `fetch_page` и в задании добавить необязательный параметр `replay_post: {"url_contains": "...", "set": {...}}`. После перехвата первого POST-запроса, чей адрес содержит `url_contains`, выполнить из контекста страницы (`Runtime.evaluate` с `fetch`) тот же запрос с телом JSON, у которого поля из `set` перезаписаны; ответ добавить в `json_responses` как ещё один элемент (`url`, `body`, `t`, `replayed: true`). Если POST не перехвачен, тело не JSON-словарь или запрос не удался, пропустить без ошибки и записать причину в журнал хаба. В части B этого НЕТ.

## Как это будет использовать бот (для понимания контракта)
Бот открывает задание, опрашивает `GET ...?since=next` примерно раз в секунду, после каждой порции разбирает текущий минимум своим парсером и сам решает остановиться: сайт сказал «готово» (`wait_for_seen`), минимум не снижался N секунд, `network_quiet` для сайтов с одним ответом, либо истёк `max_seconds`. После остановки зовёт `finish` и разбирает итог как сейчас. Проигравший дубль на втором телефоне бот отменяет через `DELETE`. Если бот упал, 15-секундная автоотмена возвращает телефон в работу.

## Порядок и выкладка
1. Часть A, тесты, выкатить на сервер (после неё в боте сразу включается сбор данных).
2. Часть B, тесты, выкатить на сервер. Бот переключается на неё сам флагом, пока старый путь остаётся рабочим.

Обратную совместимость не ломать: до выхода бота на новые маршруты всё должно работать, как работает сейчас.
